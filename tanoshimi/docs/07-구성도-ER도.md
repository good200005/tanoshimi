## 2. 인증 모듈 ER도

`email_verifications` 는 `users` 와 FK 로 묶지 않는다. 가입 전(아직 users 행이 없는 상태)에도 인증코드를 발급해야 하기 때문에 이메일 문자열로만 연결한다.

```mermaid
erDiagram
    users {
        bigint id PK
        varchar email UK "로그인 ID"
        varchar username UK
        varchar password "BCrypt 해시 (소셜 전용은 랜덤 해시)"
        boolean must_change_password "임시 비밀번호 로그인 후 강제 변경"
        enum status "active / suspended"
        enum role "user / admin"
        varchar social_provider "google / naver / line"
        varchar social_id
    }
    email_verifications {
        bigint id PK
        varchar email "가입 전에도 발급하므로 FK 없음"
        varchar code_hash "코드는 해시로만 저장"
        enum purpose "signup / find_password / change_phone"
        datetime expires_at
        int attempt_count
        datetime verified_at
        datetime used_at
    }
    phone_verifications {
        bigint id PK
        varchar phone
        varchar code_hash
        enum purpose
        datetime expires_at
        int attempt_count
        datetime verified_at
        datetime used_at
    }
    persistent_logins {
        varchar series PK "기기별 자동 로그인 식별자"
        varchar username "users.email 과 동일"
        varchar token
        timestamp last_used
    }

    users ||--o{ persistent_logins : "username = email"
    users }o..o{ email_verifications : "email 문자열로만 연결"
```

- `users` 의 유니크 키: `email`, `username`, `phone`, `(social_provider, social_id)`
- 소셜 계정과 일반 계정이 같은 이메일을 쓰는 경우 자동 통합하지 않고, 로그인 후 마이페이지에서 수동 연동한다.

## 3. 비밀번호 재발급 플로우

```mermaid
sequenceDiagram
    participant U as 사용자
    participant S as 서버
    participant M as 메일
    U->>S: 이메일 입력
    S->>S: 일반 계정인지 확인 (소셜 전용은 대상 외)
    S->>M: 인증코드 발송 (find_password)
    U->>S: 인증코드 입력
    S->>S: 코드 검증, 사용 처리
    S->>S: 임시 비밀번호 생성, 기존 비밀번호 즉시 무효화, must_change_password = true
    S->>M: 임시 비밀번호 발송
    U->>S: 임시 비밀번호로 로그인
    S->>U: 비밀번호 변경 화면으로 강제 이동
```
